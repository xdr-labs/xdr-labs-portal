## What's new in v1.1 (November 18, 2026)

Six alert-only signatures covering traffic indicators related to CVE-2026-114938 were added without modifying the existing 333 v1.0 signatures. Community detection ideas were adapted for Suricata 8.0.1, and Base64 matching was tightened after benign padded-token false positives were reproduced in testing.

| New SID | Detection indicator |
| --- | --- |
| `9006101` | Invalid-length, padded HTTP Basic Authentication Base64 |
| `9006102` | Exact 64-character Base64 test marker with invalid padding |
| `9006103` | Exact 128-character Base64 test marker with invalid padding |
| `9006104` | High-volume Basic Authentication requests (1,000 per source within 60 seconds) |
| `9006105` | JVM crash signatures exposed within HTTP response content |
| `9006106` | Suspicious padded Base64URL segment in a JWT Bearer header |

These signatures identify **suspicious network patterns**, not a confirmed Java exploit, vulnerable runtime, or successful remote code execution. Rules `9006104` and `9006105` are contextual/low-confidence indicators; deployment-specific false-positive tuning is recommended. HTTP payload detection requires plaintext visibility; encrypted HTTPS/QUIC traffic cannot be inspected without decryption.

[View the six supplemental rules](https://github.com/xdr-labs/xdr-labs-portal/blob/main/downloads/java4shell-cve-2026-114938-6.rules).

## Import into Stellar Cyber 7.0

1. **Back up the current `custom_defined.rules` file.** Import Security Rules **replaces the entire file**; do not import the six-rule supplemental file on its own.
2. Download the **complete v1.1 339-rule** file above and verify its integrity. SHA-256: `2478ffd6b3dbdfbb527695f07e00e1a106a554d8bb898a0f9584bb3845b07483`.
3. Navigate to `System → Data Source Management → Sensors → Sensors → Manage → Import Security Rules`.
4. Select the full `.rules` file and applicable sensors, then choose `Upload and Deploy`.
5. Confirm selection under `Sensor Profiles → IDS → Signature → Selected Rules`, monitor alerts/false positives and validate your actual network visibility before broad deployment.

### HOME_NET / EXTERNAL_NET and visibility

All 339 custom rules use `any any → any any` address headers, so their address eligibility does not depend on `HOME_NET` or `EXTERNAL_NET`. However, sensor capture visibility, IDS enablement, rule protocol/flow requirements, and HTTP decryption limitations still apply. Built-in ET/IDS signatures may depend on `HOME_NET`; include protected public addresses in the sensor profile as appropriate.

**Network configuration:** `System → Data Source Management → Sensors → Sensor Profiles → Feature Customization → IDS → Networks`.
